# Установка Правильных технологий

1. Загрузить `pravilnye-tehnologii-production-final.zip` в **родительский каталог document root** и распаковать: `public_html/` — сайт, `private/` — рядом, **не внутри публичной папки**. Если root называется иначе, перенести содержимое public_html в него; private оставить вне root. ZIP/инструкцию/manifest не оставлять публично.
2. PHP ≥8.2, расширение mbstring, Apache 2.4 с разрешённым .htaccess (Options/AuthConfig/FileInfo). Для nginx попросить хостинг применить эквивалентные deny/header/static/API правила; PHP встроенный сервер .htaccess не применяет. HTTPS включить в панели с учётом proxy.
3. Скопировать `private/mail-config.example.php` в `private/mail-config.php` (0600). Создать `private/request-metadata` (0700), PHP-процесс должен иметь доступ. Не загружать credentials в Git/JS/webroot.
4. В config задать `origin` = точный HTTPS origin окончательного домена без завершающего `/` (IDN в punycode); `from` = разрешённый хостингом отправитель; `rate_secret` = результат `php -r 'echo bin2hex(random_bytes(32));'`; `enabled=true`. Получатель фиксирован кодом: **zakaz@qptech.ru**.
5. Если SMTP есть: `transport=smtp`, заполнить host/port/username/password/encryption=tls либо ssl; в private выполнить `composer install --no-dev` для приложенного composer.json. Composer/PHPMailer нужны только SMTP. Если SMTP нет: подтвердить у хостинга поддержку PHP mail()/MTA и выбрать `transport=mail`. Ошибка SMTP не запускает скрытую повторную отправку через mail().
6. При стандартной структуре config находится автоматически. При другом расположении задать серверную переменную `PT_CONFIG_FILE` с абсолютным путём вне document root; data_dir/autoload в config также можно изменить. `php private/self-check.php /absolute/document-root` — диагностика CLI, без отправки/вывода секретов. Дополнительно `php -l public_html/api/request.php`.
7. Frontend уже настроен на `/api/request.php`; исходники редактировать не требуется. Открыть главную и `#/contacts`; проверить assets, поиск, варианты и корзину. Проверить HTTP: `/api/request.php` GET → JSON 405, неизвестный `/api/...` → 404, отсутствующее изображение → 404, `/private/...` и dot/backup-файлы → запрет. `#/несуществующий-маршрут` показывает 404 сайта.
8. Отправить по одной согласованной тестовой заявке: contacts → «Отправить заявку», wholesale, cart → checkout. При отправке кнопка блокируется; ошибка сохраняет форму/корзину; подтверждение транспорта показывает номер заявки. Заказ очищается только после подтверждения сервера. Не считать этот текст доказательством Inbox.
9. Проверить **Inbox и Spam zakaz@qptech.ru**, все три письма, русский текст, артикулы/варианты/количество/цены, Reply-To с валидной тестовой почтой. Подтвердить SPF/DKIM/DMARC у хостинга. Реальная доставка до этой проверки не верифицирована.
10. Проверить защиту конфигурации/metadata/logs; не включать body logging или SMTPDebug. При reverse proxy настроить доверенный REMOTE_ADDR. Сохранить финальный backup сайта и приватного config в защищённое хранилище; credentials не передавать в публичном ZIP.

Метаданные — HMAC/count/status/TTL, без PII. Лимит 5 попыток/IP/15 минут, dedupe 24ч; не очередь. Для уборки expired-файлов временно disabled endpoint, дождаться окончания запросов, удалить metadata с expires < now. Не удалять активные lock-файлы. Pending после обрыва проверять по ящику перед повторной отправкой.

GitHub Pages — отдельный preview с пустым endpoint и честной подготовкой письма; PHP там не запускается. Пакет содержит те же frontend/assets, отличается только публичным request-config и серверной структурой.

Apache правила требуют разрешения хостинга: [официальная документация .htaccess](https://httpd.apache.org/docs/2.4/howto/htaccess.html). При 500 не удалять защиту целиком: хостинг должен разрешить нужные directives либо перенести их в server config.
